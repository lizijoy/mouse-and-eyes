# 什么时候不该用这套东西

写工具的人有责任说清楚它什么时候会坏。这一页比 README 更值得先读。

---

## 一、目标窗口是 Chromium / Electron 系

**症状**：`pywinauto`、UIA、MSAA 全查不到控件，只看到一个 `Chrome_WidgetWin_1` 的大窗口。

**原因**：Chrome、Edge、VS Code、Discord、Slack、大量国产桌面端（很多 NAS 客户端也是）都是
Chromium 内核。它们把整个界面画在一张画布上，对 Windows 的无障碍接口只暴露了很薄的一层。

**后果**：

- 控件级方案（找按钮名字、读输入框内容）基本失效；
- 只剩两条路：**坐标点击** 或 **视觉模型**；
- 坐标点击意味着：分辨率、DPI、主题、窗口大小，动一个就全废。

**这个仓库适合的**，是那些"能看到传统控件"的程序（Win32 老软件、部分 Qt 程序、系统设置）。

---

## 二、DPI 缩放不是 100%

**症状**：坐标总是差一点，或者模板匹配永远对不上。

**原因**：Windows 有 DPI 虚拟化。一个 150% 缩放的屏幕上：

- `GetWindowRect` 给你的可能是**逻辑像素**；
- 而 `SetCursorPos` 用的是**物理像素**；
- 两者差 1.5 倍。

**怎么检查**：

```powershell
# 物理分辨率
(Get-CimInstance Win32_VideoController | Select-Object -First 1).CurrentHorizontalResolution
# 逻辑分辨率
[System.Windows.Forms.Screen]::PrimaryScreen.Bounds.Width
```

两个数不一样，就说明打开了缩放。

**临时解法**：把目标进程设成 DPI 无关，或者全程只用物理像素（本仓库的
`CopyFromScreen` + `SetCursorPos` 组合在 100% 下是一致的，其他比例需要你自己换算）。

---

## 三、目标窗口用硬件加速渲染

**症状**：`Get-WindowBitmap`（PrintWindow）抓出来是全黑。

**原因**：D3D / OpenGL 直接往显卡画，不经过 GDI 的表面，
PrintWindow 拿不到内容。

**解法**：只能把窗口搬到前台，然后截屏（`Get-ScreenBitmap`）。
代价是必须抢前台，而抢前台本身就不保证成功。

---

## 四、你要做的是"业务流程"，不是"点几下"

如果需求是：每天登录某系统、导出一张表、发一封邮件 —— 而那个系统**有 API**，
**那就用 API**。GUI 自动化永远是最后手段。

判断顺序应该是：

1. 有官方 API / CLI？用它。
2. 有数据库 / 文件可以直接读？用它。
3. 有浏览器页面？用 Playwright / Puppeteer 操作 DOM，比点像素稳一万倍。
4. 以上都没有，才轮到本仓库。

这一条是血的教训：为了"点一个按钮"去写 GUI 自动化，
而那个按钮背后其实是一个 HTTP 请求 —— 这是最常见的浪费时间方式。

---

## 五、屏幕锁屏 / 远程桌面断开

**症状**：脚本在有人看着的时候跑得好好的，一锁屏就全乱。

**原因**：

- 锁屏后桌面窗口不可见，截图是锁屏界面；
- 最小化的窗口 `GetWindowRect` 可能返回奇怪的值；
- RDP 断开后会话进入"无显示器"状态，GDI 截图会失败。

**解法**：

- 需要 24 小时跑的，别用 GUI 自动化，用服务 + API；
- 必须在交互会话里跑的，保持会话解锁（或用 `tscon` 把会话重定向回控制台）。

---

## 六、杀毒软件 / EDR

自动点鼠标的脚本，行为特征和木马高度相似。企业环境里被拦是正常的。

不要试图绕过。要么加白名单，要么换方案。

---

## 七、生产环境的选择

| 需求 | 建议 |
|------|------|
| 只要点几下，一次性的 | 本仓库够用 |
| 要长期稳定跑 | 找 API，或者用 Playwright |
| 界面是 Electron，且必须操作 | 上视觉模型（OmniParser / UI-TARS），别用坐标 |
| 企业内部批量 | 用商业 RPA（UiPath、影刀），它们处理了 DPI/多屏/权限 |

**这个仓库的定位是"教学 + 兜底"，不是"生产框架"。**
